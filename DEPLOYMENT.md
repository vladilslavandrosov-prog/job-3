- **Telegram Bot** (уведомления, через @BotFather)

## 1. Создание сервиса на хостинге (пример — Amvera)

1. В Amvera создай новый проект → подключи Git-репозиторий `vladilslavandrosov-prog/job-3`, ветка `main`
2. Конфигурация сборки уже описана в `amvera.yaml` в корне репозитория — Amvera подхватит её автоматически:
   - окружение: Node.js 20
   - команда сборки: `npm run build`
   - команда запуска: `sh start.sh` (стартует Next.js + Telegram-бота параллельно)
   - порт контейнера: 3000
3. Запомни/скопируй домен, который выдаст хостинг, например `https://job-3-vladis-XYZ.amvera.io` — он понадобится в переменных окружения и в настройках Supabase/ЮKassa

## 2. Supabase: база данных и аутентификация

### 2.1. Проект Supabase
- Если переиспользуешь старый проект Supabase — пропусти создание, просто возьми его ключи (Settings → API)
- Если создаёшь новый — создай проект на [app.supabase.com](https://app.supabase.com), дождись инициализации

### 2.2. Применение миграций (только для нового проекта или если таблиц нет)
Открой Supabase → **SQL Editor → New Query** и выполни по очереди содержимое файлов из `supabase/migrations/`:
1. `001_initial_schema.sql` — создаёт таблицы `tenants`, `tenant_users`, `telegram_users`, `saved_tenders`, `payments` и базовые RLS-политики
2. `002_auth_trigger.sql` — триггер, который автоматически создаёт `tenant` при регистрации пользователя
3. **`003_fix_tenant_users_rls_recursion.sql`** — ОБЯЗАТЕЛЬНО. Без неё политика RLS на `tenant_users` рекурсивно обращается сама к себе, и любое сохранение тендера или создание тенанта падает с ошибкой `infinite recursion detected in policy for relation "tenant_users"`

Миграции не применяются автоматически при деплое (CLI-раннер не подключён) — это разовая ручная операция.

**Проверка**: в Table Editor должны появиться все 5 таблиц выше.

### 2.3. URL Configuration (обязательно после каждого изменения домена)
Supabase → **Authentication → URL Configuration**:
- **Site URL**: `https://ТВОИ_ДОМЕН` (без слеша в конце)
- **Redirect URLs** — добавь оба:
  ```
  https://ТВОИ_ДОМЕН/api/auth/callback
  http://localhost:3000/api/auth/callback
  ```

Без этого письма для подтверждения почты/сброса пароля будут вести на неправильный домен (классическая ошибка — ссылка ведёт на `localhost:3000`).

### 2.4. Google OAuth (опционально)
Supabase → **Authentication → Providers → Google**:
1. Включи провайдер
2. В [Google Cloud Console](https://console.cloud.google.com) создай OAuth 2.0 Client ID (тип Web application)
   - Authorized redirect URI: `https://ТВОИ_ПРОЕКТ.supabase.co/auth/v1/callback`
3. Скопируй Client ID и Client Secret в настройки провайдера в Supabase

### 2.5. Ключи для переменных окружения
Supabase → **Settings → API**:
- `Project URL` → `NEXT_PUBLIC_SUPABASE_URL`
- `anon public` → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `service_role` (секретный!) → `SUPABASE_SERVICE_ROLE_KEY`

## 3. ЮKassa: приём платежей

### 3.1. Ключи API
Личный кабинет ЮKassa → выбери тестовый или реальный магазин → **Интеграция → Ключи API**:
- `shopId` → `YUKASSA_SHOP_ID`
- Секретный ключ (начинается с `test_` для тестового магазина) → `YUKASSA_SECRET_KEY`

### 3.2. HTTP-уведомления (вебхук)
**Интеграция → HTTP-уведомления → Изменить настройки**:
- URL для уведомлений: `https://ТВОИ_ДОМЕН/api/billing/webhook`
  - ⚠️ Частая ошибка — указать `/pricing` или другой URL вместо `/api/billing/webhook`. Без правильного URL оплата проходит, но статус тарифа в приложении не обновляется
- Включи события: `payment.succeeded`, `payment.waiting_for_capture`, `payment.canceled`, `refund.succeeded`

ЮKassa **не подписывает** вебхуки секретным ключом — заголовка `x-yukassa-signature` не существует. Переменная `YUKASSA_WEBHOOK_SECRET` в коде больше не используется и не нужна. Для защиты от поддельных запросов в продакшене используй IP-вайтлист ЮKassa (список IP в их документации API), не HMAC-секрет.

### 3.3. Тестовая оплата
Тестовая карта: номер `5555 5555 5555 4444`, любой будущий срок (напр. `12/28`), любой CVV (напр. `123`). После оплаты в ЮKassa → **Интеграция → Лог событий** можно проверить, дошло ли уведомление до `/api/billing/webhook` и какой код ответа вернул сервер (должен быть 200).

## 4. Telegram-бот (опционально)

- `TELEGRAM_BOT_TOKEN` — получить у @BotFather в Telegram (`/newbot`, если бот ещё не создан)
- Бот стартует автоматически вместе с Next.js (см. `start.sh`), читает те же переменные Supabase
- Привязка аккаунта пользователем: `/dashboard/settings` → «Telegram» → «Подключить» → код → в боте `/start connect_КОД`

## 5. Переменные окружения хостинга

Внести в Amvera (или другой хостинг) → раздел переменных окружения для этапов **Сборка** и **Запуск**:

| Переменная | Откуда |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Settings → API |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase → Settings → API (секретный) |
| `YUKASSA_SHOP_ID` | ЮKassa → Интеграция → Ключи API |
| `YUKASSA_SECRET_KEY` | ЮKassa → Интеграция → Ключи API (секретный) |
| `NEXT_PUBLIC_APP_URL` | Домен хостинга, без слеша в конце |
| `NEXTAUTH_SECRET` | Сгенерировать: `openssl rand -base64 32` |
| `TELEGRAM_BOT_TOKEN` | @BotFather (если используется бот) |
| `FLASK_BACKEND_URL` | Только если есть отдельный Flask-сервис; иначе можно не задавать |

Полный список с примерами значений — также в `.env.local.example` в корне репозитория.

## 6. Проверка после деплоя (по порядку)

1. **Сборка прошла** — в логах хостинга нет ошибок `npm run build`
2. **Регистрация**: `/register` → письмо с подтверждением → ссылка ведёт на правильный домен (не localhost) → редирект на `/onboarding`
3. **Вход**: `/login` → попадаешь в `/dashboard`
4. **Сохранение тендера**: на карточке тендера нажать ✓/✗/⏸ → должен появиться в «Сохранённые» (если упадёт с 500 — почти наверняка не применена миграция 003)
5. **Оплата**: `/dashboard/settings/subscription` → выбрать тариф → тестовая карта → после оплаты тариф должен обновиться сразу (если не обновился — проверить лог событий ЮKassa и URL вебхука)
6. **Telegram** (если используется): привязка аккаунта и получение уведомлений
